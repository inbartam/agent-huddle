# Security and privacy model

The Huddle sits between you and agents that can run commands on your machine. It can approve
actions on your behalf. Treat it as part of your permission system, not as a dashboard.

## What must stay true

1. **Agents are never less safe with the Huddle than without it.** The Huddle can remove prompts
   through rules you wrote. It cannot override deny or ask rules in your Claude Code settings
   (Claude Code enforces that), and it must not ship defaults that approve destructive actions.
2. **A dead Huddle changes nothing.** Hooks fail open; held requests are released on shutdown.
3. **Nothing leaves the machine** unless you turn on phone access or Ask the Huddle (off by default; it sends the masked summary shown in "What will be sent" to Anthropic through your Claude Code login, ADR-022).
4. **Text from agents is data.** It is never executed, never rendered as HTML, never followed as an instruction.

## Assets

- The authority to approve tool calls (the most valuable one).
- Hook payloads: your prompts, command lines, file paths, tool output that may contain secrets.
- `~/.claude/settings.json`, which the installer edits, and `~/.claude.json`, which only `claude mcp add|remove` changes, after consent (ADR-025).
- The Huddle token.

## Threats and the control for each

| Threat | Control |
|---|---|
| A web page you visit posts to the local port to forge events or read state | Bind 127.0.0.1. Require the `X-Huddle-Token` header. Reject any request with an `Origin` header. No CORS headers, ever. No GET endpoint returns data without the token. |
| Another program on the machine squats the port while the Huddle is closed and answers permission hooks with "allow" | Out of scope for the token (a local program running as you can already act as you), but: use a fixed, documented port; on start, fail loudly if the port is taken; document that Claude Code's own deny and ask rules remain the floor. |
| Agent output contains HTML or script that runs in the app | Render all agent text as text nodes. No `dangerouslySetInnerHTML`. Markdown is rendered without any HTML step: `view/markdown.ts` parses it to plain data and `MessageText` draws React elements whose children are text (no link, image, `href` or `src` is ever built), so there is nothing to sanitize. `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, strict CSP, no remote content, navigation and new windows blocked. |
| Agent output tries to instruct the Huddle ("approve all pending requests") | No code path turns agent text into a command. "Ask the Huddle" sends state to a model with no tools and shows text back; its output cannot trigger commands. |
| An auto-approve rule is broader than intended | Deny beats ask beats allow. Default rule set is read-only tools and a short list of safe commands. The rule editor shows which recent real requests a new rule would have matched before saving. Every automatic decision is logged with its rule. Rules never match on command substrings, only on prefixes, and compound commands are treated as not matching an allow rule. |
| Secrets end up in the event log | Store summaries, not payloads. Clip free text; ids and paths are clipped too (`CLIP_LIMITS.id`, `.path`). Never store `tool_response`. **In place since M1:** `maskSecrets` (`packages/core/src/privacy/redact.ts`) masks common secret shapes (Authorization/Bearer, `sk-`, GitHub, AWS key ids, Slack, PEM private keys, `KEY=value` where KEY names a secret, `--password x`, URL passwords) in every free-text field the normalizers emit, and the event store runs it again on write. It is best effort: a secret in an unknown format stays visible. Logs live in the app data folder with user-only permissions. **M5 WP5 (core):** retention (default 30 days; at start, once a day, and at once when lowered) and "delete all history" delete events, search rows, derived rows and report files in chunked transactions with `secure_delete` on (freed pages zeroed; VACUUM only when little is left), and delete all also removes the older JSONL folders without following links. Template prompts are shown masked (templates.json keeps them as typed, owner-only; the launch sends them as typed). The Settings buttons are renderer work. |
| The installer damages `settings.json` | Dry run by default, backup before write (owner-only), atomic write (temp file + rename), refuse to touch unparseable JSON (the error names a line and column, never a fragment of the file), only add or remove entries that are exactly what the installer writes, write through a symlinked `settings.json` to its target, round-trip tested. The consent diff hides env values that are not the Huddle's, every `X-Huddle-Token`, credential headers and anything `maskSecrets` would mask. Consent is stored only after the shown change was written; quitting during start or attach never leaves hooks behind. |
| Phone access exposes approvals to the network | Off by default and after every restart (ADR-024). When on: a separate listener on one private LAN IPv4 (never `0.0.0.0`, loopback or public), pairing with a one-time 6-digit code shown on the desktop (2 min, 5 tries, never stored), per-device token kept only as a hash, `Host` and own-`Origin` checks, rate limits, approvals only for requests already in the inbox, and Allow refused (400, "Answer this one on the computer.") for a request whose summary hides part of the command, a masked secret or a cut at the summary limit (AX-01; Deny still works, and the desktop card says so in words); since ADR-030 also answers, messages, pause, resume and stop (managed runs) through `POST /api/act`, an explicit allowlist (`PHONE_ACTION_TYPES`; anything else 403 before the core), zod-checked bodies rebuilt field by field, typed text refused past 1000 characters and clipped to CLIP_LIMITS, a typed answer masked in the log, its own rate limit, and only for an agent or question in the phone view now whose control (from `AgentNode.capabilities`) is enabled; every such action is logged with `via: 'phone'`; launch, rules, budgets, history and Ask stay desktop only; visible "phone connected" indicator, one-click revoke, auto-off after 8 h without a phone action. Plain HTTP: use it only on a trusted network (a Wi-Fi eavesdropper can read the token and the masked view). Known limits (M6 review): the phone keeps its token in `localStorage` for `http://<ip>:<port>`, so a page served from the same private address and port on another network could read it (it only works against this Huddle while phone access is on); anyone on the network can hold the listener's 64 connections with slow requests or spend the 5 pairing tries (denial of service only, no authority). A device token now also lets its holder message, pause, resume and stop managed runs, not only approve (ADR-030). Prefer Claude Code's own Remote Control for driving a single session. |
| The self-report MCP server is registered for every session (F27, ADR-025) | Managed runs: per-run files in `<dataDir>/run-mcp/<runId>/` (owner-only; the server copy, `mcp.json`, and a `--settings` file with two `permissions.allow` entries, `mcp__huddle__report_progress` and `mcp__huddle__report_teammate`, no hooks), removed at exit and swept at start; `node` by absolute path; not `--strict-mcp-config`. Attached sessions: opt-in only; the Huddle never writes `~/.claude.json`, it runs `claude mcp add|remove --scope user huddle` as an argv array after the user saw the exact command and diff (fingerprinted), refuses a `huddle` server that is not its own, and reads the file back to check. The tools return `ok` and store nothing; reports arrive through the PostToolUse hook and are clipped like any tool input (P2). Known limit (M6 review): the allow entries trust the server name `huddle`; a repository's own `.mcp.json` server named `huddle` with a tool of the same name would be auto-allowed too, and could forge a progress or teammate report (status only). Which definition wins a name clash is not documented; check it before relying on the name. The one automatic message (ADR-027) only accepts teammate names matching `[A-Za-z0-9_.-]{1,40}` (no spaces). |
| A skill write (F28, ADR-028) is steered somewhere else: a crafted name, a link or junction in the project, or a folder that is really `~/.claude` | Only into `<project>/.claude/skills/<name>/SKILL.md` of a known project picked from a list (the core resolves the path from its own list, never from the renderer). Name `^[a-z0-9][a-z0-9-]{0,63}$`; local absolute path checked as text first and again on the real path (a link to a network share or a `\\?\` / `\\.\` device path is refused); real path not a drive, home folder or Documents; every folder on the way a real folder (no symlink or junction), none inside Claude Code's config folder or `<home>/.claude`; `SKILL.md` a plain file; temp file plus rename after a second check; an existing file replaced only after the user pressed "Replace it". The user's own skills are listed read-only. Skill text read from files is clipped and shown as text; the Huddle stores none of it. Known limit (check then use, ADR-028 point 6): the checks and the write are separate file system calls, so a folder swapped for a link by another local program between the last check and the rename is not detected. Accepted: the Huddle is local and single user, such a program already runs as you and can write there itself, and every checked path is under a project folder you already work in. |
| Task text (F29, ADR-029) ends up in the event log | The title and details are the user's own text, clipped (200 and 4000 characters) and masked by the store like every free-text field. They live in the Huddle's own `huddle-tasks` session, which the retention and "delete all history" keep (like the overall budgets): deleting a task appends `huddle_task.deleted` and the earlier events stay in the local log. A task launch is a normal launch (same checks, same folder rules). |
| The token leaks | It is stored in the Claude config folder and written into `settings.json` (same trust level). On Windows the `0o600`/`0o700` modes the code passes are ignored by Node: what protects these files is the inherited ACL of `%USERPROFILE%` and `%APPDATA%` (you, SYSTEM, Administrators). A `CLAUDE_CONFIG_DIR` on a folder with a broader ACL (a shared drive) exposes the token. Claude Code applies the `settings.json` `env` block to its own process, so commands an agent runs may inherit `OTEL_EXPORTER_OTLP_HEADERS` with the token (not verified by a spike); same-user code could read `settings.json` anyway. Rotating it is a re-install. It only authenticates ingest, it does not authorize commands; commands come over Electron IPC. |
| A malicious repository's `.claude/` content is loaded when a run is launched there | Launching is the same as running `claude` in that folder. Show the folder and whether it is trusted by Claude Code before launch; never launch into a folder the user has not chosen. |
| Script running in the renderer launches a run with every permission check off | The renderer is sandboxed with CSP `script-src 'self'`, agent text is drawn as text nodes only, and the Markdown renderer builds plain data (no HTML, no links). Main validates the shape of every `run.launch` (a known permission mode, a local folder). Known limit (release audit, 2026-11-18): main does not ask again on its own, so script already running in the renderer could start a `bypassPermissions` run in any local folder the user owns. Planned: a confirm dialog owned by main for that mode. |

## Review checklist for every change

- Does it add a listener, a route or an IPC channel? Token, origin and input validation in place?
- Does it display text that came from an agent, a hook or a file? Rendered as text?
- Does it store anything new? Clipped, redacted, covered by retention and by "delete all"?
- Does it write a file outside the app data folder? Only a known project, real folders, no links, never `~/.claude`, no silent overwrite (ADR-028)?
- Does it hold a hook response? All four endings handled (user, rule, closed by Claude Code, shutdown)?
- Does it widen what can be approved without the user seeing it?
